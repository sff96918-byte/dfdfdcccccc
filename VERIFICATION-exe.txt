What revision 24 adds over 23 (the desktop app):

  * One click on Windows: build-exe.bat finds Python (an existing .venv, else
    "py -3", else python), installs requirements-build.txt, runs tools\verify.py,
    packs dist\ChitChatBot\ChitChatBot.exe with PyInstaller from
    build/ChitChatBot.spec, and finishes by running the packed app's own
    --selftest. Double-click the exe from then on.
  * The exe is the same dashboard in its own window: pywebview on the system
    WebView2 - the engine the Go/Wails build used - with the Go window's title,
    1280x820 (minimum 1080x700) and background #161716. The build is windowed
    (no black console); --debug / --diag / --selftest / --browser / --port /
    --data / --allow-multiple are there for support from a Command Prompt.
  * chitchatport/runtime.py owns every packaged-app path: resource files come
    from the bundle (sys._MEIPASS), data/ lives next to the exe, a read-only
    install falls back to %LOCALAPPDATA%\ChitChatBot\data and says so in the
    log, a bundled fixed-version WebView2 folder next to the exe is honoured
    (WEBVIEW2_BROWSER_EXECUTABLE_FOLDER, exactly like the Go build), and the
    single-instance lock never blocks a start after a crash.
  * No Go settings anywhere: the eight Go worker-engine timings are gone from
    the settings model (settings.REMOVED_GO_TIMING_FIELDS), from the dashboard
    and from what a save writes. general.json holds exactly the seven settings
    this port owns. An old Go-era file still loads: the unknown keys are ignored
    and dropped the next time the Settings are saved (covered by tests).
  * tools/frozen_smoke.py - the check that makes this revision honest on a
    machine that cannot produce a .exe: it lays out a PyInstaller-shaped bundle
    in a temp folder (ChitChatBot\ChitChatBot "exe" + ChitChatBot\_internal\),
    starts the real app with sys.frozen and sys._MEIPASS set, and proves the
    bundle is really used: --selftest and --diag read the bundled UI, the
    bundled Go reference copies and the bundle's own data/ folder, the dashboard
    is fetched over HTTP from the bundled ui/ folder, a settings save lands in
    <bundle>/data/state/general.json with the seven Python keys and nothing from
    Go, the log file appears next to the exe, a second start is refused with the
    running pid, and a killed run's stale lock is taken over.
  * tests/test_runtime.py - 21 tests for exactly those paths, so the behaviour
    is pinned on every machine, not only inside a built exe.

How to build it on your PC (Windows, one click):

  build-exe.bat                              -> dist\ChitChatBot\ChitChatBot.exe

The result is a folder: ChitChatBot.exe, its _internal\ folder and, after the
first start, its own data\ folder (settings, logs, chat, state). Zip the folder
to move the app to another PC. A single-file exe was rejected on purpose: it
would unpack ~200 MB to a temp folder on every start.

That run is also how four Windows-only problems were found and fixed - none of
them could show up on Linux, and all of them would have stopped build-exe.bat on
this machine:

  1. tests/test_proxy_relay.py wrote its throwaway certificate to "/tmp/...": on
     Windows a leading slash means "<current drive>:\tmp", which does not exist
     on a fresh machine. It now goes through tempfile.
  2. tests/test_runtime.py mocked sys._MEIPASS with "/tmp/..." and compared
     .as_posix(); the code resolves the bundle folder, so on Windows the result
     is "C:/tmp/..." - the assertion was testing the operating system. It now
     uses a real temporary folder and compares Path objects.
  3. tests/test_runtime.py compared the raw folder name from tempfile with the
     folder the app reports: Windows hands back the short 8.3 name
     (C:\Users\RUNNER~1\...), the app reports the long one
     (C:\Users\runneradmin\...). Resolved paths are compared now.
  4. tests/test_dashboard_api.py asked the running server for /api/diagnostics,
     whose default is the deep check that really launches a browser; a machine
     with no browser Playwright can start (the CI runner) sat in two 30-second
     launch timeouts and the request timed out instead of answering. The test is
     about the route's default, so it patches the launcher.

  Two tool fixes came out of the same runs: the helper processes in
  tools/verify.py and tools/frozen_smoke.py now always speak UTF-8 (a Windows pipe
  is not UTF-8, which used to make the frozen-layout check fail for an unrelated
  reason), and a failing CI step repeats its key lines as annotations, because the
  raw step log lives behind a URL that not every environment can fetch.

  Note for the operator: install.bat printed the verification result but did not
  act on it, so these Windows-only failures stayed invisible there. build-exe.bat
  and the GitHub workflow both stop on the first failing check.
